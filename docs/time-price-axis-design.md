# 时段价与目录价：把时间轴从「折扣」搬到「价格」

> 状态：**设计已定稿**（2026-11-20）；实施按 §8 推进
> 关联：`setting/ratio_setting/group_time_ratio.go`（Layer 4 现状）、`setting/ratio_setting/group_model_ratio.go`（解析链）、`docs/group-management-redesign.md` §3、`pkg/billingexpr/expr.md`
> 一句话：把时间轴从「折扣」搬到「价格」——`Final = 常规价 × 时段系数`，折扣层从此与时间无关。

## 1. 问题：时间轴长在折扣上

现状（`ResolveGroupRatioAt`）：

```
Layer 0  Base  = GroupRatio(线路)
Layer 1  Base ← GroupGroupRatio(用户分组, 线路)        身份，命中即覆盖
Layer 2  常规  = Base × GroupModelRatio(线路, 模型)     multiply / override
Layer 4  终值  = Base × 时段值                         ★ 命中时段则**取代** Layer 2
Layer 3  终值 × UserGroupModelRatio(用户分组, 模型)     档位，永远最后
```

即：**唯一会随时间变的量是「折扣」**。`group_time_ratio.go:181` 的校验还把时段值锁在
`(0, 1]`——「只打折、不加价」，因为它在折扣轴上，加价不是一个折扣该干的事。

这套语义带来四个具体问题：

1. **折扣率不再恒定。** 模型广场的折扣角标读的是 `usedGroupRatio`（= 终值，含时段，
   `PricingTableColumns.jsx:225`），同一客户同一模型白天 8 折、夜里 5.6 折。日志
   `other.group_ratio` 同理——任何按它统计「平均折扣」的报表拿到的都是随时段漂移的混合值。
2. **「优惠金额」无法归因。** 对账要回答「这个客户这个月我们让了多少」，答案必须拆成
   「合同折扣让的」与「时段价让的」。现在两者被压进一个系数，拆不出来。
3. **改折扣要连带改时段值。** 时段值 0.56 的语义是「相对 Base 的绝对系数」，它把当时的
   0.8 折烤进了数字里。模型折扣一改，时段值不会跟着走——编辑器只能靠「时段值高于常规值时标红」
   打补丁，而这条告警只在它变成「加价」时才触发，多数情况是静默算错。
4. **高峰加价表达不出来。** `(0,1]` 的约束下想表达「高峰是空闲的 1.5 倍」，只能反过来把
   高峰价当基准、把空闲配成 0.67——于是「常规价」在价目表上是个虚数，而客户看到的是
   「夜里给你打 6.7 折」，不是「夜里价目更低」。

override 组合还有个更硬的 bug，见 §4.2。

## 2. 行业口径：变的是价目表，不变的是折扣

两条外部证据：

- **Oracle 的 CPQ / 计费产品文档**（Communications 26B 发布说明）把 "Time of the day
  pricing" 列为一种**定价模型**（配 Peak / Off Peak 时段的 Price），与 discount models
  （`discount fixed` / `discount percentage` / `grant allowance`）是并列的两类东西。
  时间维挂在「价」上，不挂在「折扣」上。
- **DeepSeek 的峰谷价目表**：峰谷是同一张价格表的两个单价列，**高峰价 = 空闲价 × 2**，
  高峰时段写死为「周一至周五 9:00-12:00、14:00-18:00」。它们调整的是价目表本身
  （2026-08-23 那次把周六周日全天并入空闲价），而不是给客户改折扣率。

为什么这个划分是必须的，不是品味：

| 面向 | 需要恒定的东西 | 为什么 |
|---|---|---|
| 商务合同 | 折扣率（8 折、返点） | 折扣写进合同。折扣率随时间变，等于合同一天改两次 |
| 财务对账 | 「优惠金额」按来源拆分 | 收入 = 价目 × 用量 × 折扣；优惠 = 价目 × 用量 × (1−折扣)。两者都要能独立归因 |
| 成本核算 | 成本比的分母 | `ChannelCostModal` 的「成本比 = 上游成本 ÷ 目录价」里，分母必须是公开价目，不是此刻成交价 |
| 对外披露 | 「原价划线 + 折扣」 | 原价随时段变是常态且正当（促销/时段价目）；折扣数变，客户会读成「你对我的合同偷偷改了」 |

## 3. 目标模型：价格轴 × 折扣轴

```
目录价      ModelRatio(模型)                     全局，恒定（标准价目）
时段系数  × 时段系数(模型, 此刻)                  ★ 全链路唯一的时间来源，全局按模型
线路基准    GroupRatio(线路) / GroupGroupRatio(身份，覆盖)   恒定
常规价    = 线路基准 × 模型规则(multiply | override)         恒定   ← 「原价」的此刻口径
实付      = 常规价 × 时段系数 × 用户档折扣                    折扣永远最后乘
```

一行代码概括这次改动：`Final = NormalRatio × 时段系数`，而不是 `Final = Base × 时段值`。
时段系数的索引是**模型**，与线路无关（v1 决定，理由见 §3.1）——所以同一个模型在任何线路上
都是「该时段打同一折」，线路之间只差一个恒定的基准倍率。

与现状的**唯一**结构差异就一行：`Final = NormalRatio × 时段价系数`，而不是
`Final = Base × 时段值`。

四条不变量（后面所有取舍都从这四条推）：

1. 全链路只有一个时间来源，且它在价格轴上。集合内不存在第二个按时刻变化的乘数。
2. 折扣层（模型乘数、身份、档位）与时刻无关 —— 这是「折扣恒定」可对外承诺的前提。
3. 时段价系数**只乘一次**，作用在「常规价」上（含 override 得出的锁价，见 §4.2）。
4. 时段价系数必须在**解析链内**求值，不能挪到展示层：文本走 `PriceData.GroupRatioInfo`、
   异步任务走 `BillingContext.GroupRatio`，冻结机制才自动继承（`e27ab74c3` 已验证过这条路径）。

它能表达而现在表达不了的：某模型「标准 ¥x / 闲时 ¥0.7x / 高峰 ¥1.5x」，且客户侧恒为「8 折」。

### 3.1 索引：全局按模型（v1 决定）

**决定（2026-11-20）：v1 只做全局层，不提供「指定线路」的作用域。**

这是业务事实决定的，不是技术偏好：**目录价全网一份**。自建算力和供应商渠道的成本不同，
但那是我们的成本，客户看到的目录价不该因此不同。所以「某条线路有自己的一套时段价」
在这门生意里根本不该存在——它会把成本差异泄漏成价目差异。

连带一个必须写清楚的结论：**原 Layer 4 的动机（自建 GPU 夜间空闲、边际成本低）不再表现成
「线路级的价」**，而是表现成「我们对全网公布的时段价」。成本侧的时段差进不了售价模型，
它只影响毛利。想拉夜间负载，靠的是公布夜间低价，而不是给自建线路单独降价——
后者会让同一个模型在不同线路上出现两个价，客户一旦发现就没法解释。

于是整条链只剩下**一个时间维、一个索引**：

```
目录价 × 时段系数(模型, 此刻)     ← 唯一的时段层，全局
```

省掉的东西（按影响面排）：

| 简化 | 少掉的东西 |
|---|---|
| 作用域下拉 | 线路名软引用、孤儿规则、同名重建复活、删线路级联、体检新增 source —— 整组生命周期问题消失 |
| 存储两层 | 不需要 `global_rules` + `rules` 两段，规则表就一层：模型模式串 → 时段列表 |
| 解析与展示 | `pickTimeRule(model, at)` 只按模型查；`/api/pricing` 的时段视图从 `group_time_ratio[g][m]` 收敛成 `model_time_ratio[m]` |
| 互斥判定 | 时段价与 `tiered_expr` 的时间函数都落在模型维，粒度天然对齐（§4.3） |
### 3.1.1 但不能把 `ModelRatio` 本身变成时间的函数

这是本节唯一一条硬约束。`ModelRatio` 是 `map[string]float64`，被约 20 处读，其中几处读的是
**「标准目录价」这个语义本身**，不是「此刻售价」：

- `ChannelCostModal`：「成本比 = 上游成本 ÷ 目录价」。目录价若随时钟变，成本比就成了时间的函数，
  而它本该是一个**稳定**的供应商折扣系数（"这家给 62 折"），一变就没法用。
- 订阅套餐折算、积分价预览（「按未打分组折扣的列表价估算」）：对外承诺的"套餐值多少钱"
  不能白天一个数、夜里一个数。
- 视频计费矩阵的锚点、单位迁移换算：都是"标准价目"的消费者。

所以正解是**另加一个系数层**乘在 `ModelRatio` 上（本节的「目录价时段」），
让 `ModelRatio` 继续只表示标准价目。这样 §7 那 20 处消费方一行都不用改，
而效果与"目录价动态"完全相同。


### 3.2 v1 之后剩下的两个边界

原来为「按线路作用域」准备的那一整套（软引用、删序、重建复活、级联、体检 source）**全部不需要**，
因为全局层不引用任何名字。只剩两件小事：

**一、模型名孤儿。** 时段价按模型模式串索引，模型从 `ModelRatio` 删掉后规则会成为孤儿。
但它没有线路那一套危险：模型名是稳定标识，不会像组织结构那样改名重建；而且编辑器已经有
「未匹配」橙标（`stale_rules`），把它从「本线路无渠道覆盖」扩成「全站已无此模型」就够，
不需要级联、不需要时序、不需要事务。

**二、存量是按线路存的，要摊平。** 现网形状是 `{线路: {模型: [...]}}`，改全局后必须是
`{模型: [...]}`。这跟 §5 的「取代 → 叠加」换算属于同一次迁移里的两步：

1. **换算值**：`tf = tv / D`（multiply），override 见 §5.1（多数可精确保价换算）；
2. **摊平线路**：按 `(模式串, 模板)` 聚合，各线路算出的 `tf` 一致 → 自动合并；
   不一致 → 逐条列出人工选一个。

第二条不是理论风险：**两条线路对同一模型配了不同时值时，合并后必有一条线路的价格要变**。
预览表表头必须明写这句话，让运营看见的是「选 A 还是选 B」，而不是一个静默的结果。
现网如果只有少数线路配过时段规则，冲突大概率是空的。


## 4. 与现有机制逐条冲突分析

### 4.1 与「取代」语义：必须改成叠乘，且数值会变

今天是取代，明天是叠乘，两者数值不同。换算在 §5 给出——注意**只在「时段规则」与
「模型规则」同时命中时**数值才会变；没有模型规则时 `NormalRatio = Base`，改成叠乘后逐位不变。

这条冲突不是可以绕开的：要「折扣恒定」，时段系数就必须乘在折扣上，而「乘在折扣上」
就是叠乘。**「折扣含时段」与「时段含在价里且折扣独立」二者只能选一个**，没有第三种。

### 4.2 与 override（锁价）：旧行为是一个 bug，新行为要人工确认

设 premium 线路基准倍率 1.5，GLM-5 用 `override = 2.2`（供应链成本高，精确锁价），
又配了时段价「夜间 0.7」：

| | 计算 | 结果 |
|---|---|---|
| 旧 | 时段命中 → `Base × 0.7` = 1.5 × 0.7 | **1.05**，锁价 2.2 被整条吃掉 |
| 新 | `NormalRatio × 0.7` = 2.2 × 0.7 | 1.54，锁价打折 |

旧行为下这段配置从「2.2 的 7 折」变成「基准倍率的 7 折」，管理员配的时候完全看不出来：
夜间价一夜之间从 1.54 掉到 1.05，而页面上写的仍是「夜间 0.7」。这是当前设计里最该修的一条。

新行为没有这个问题（时段价永远乘在常规价上），代价是**这个组合无法自动换算**：
要让旧值 1.05 保持不变，需要 `时段价 = 1.05 ÷ 2.2 = 0.477`，而它依赖 Base，而 Base 又被
`GroupGroupRatio[用户分组][线路]` 覆盖——逐用户分组不同。所以必须人工确认（§5.3）。

顺带决定：**override 不豁免时段价**。允不允许「锁价 × 时段价」是配置意图问题，
用 override + 时段规则本身就说明管理员要的是「这条线路这个模型夜间也便宜」；
真要绝对锁价，别配时段规则。UI 上给提示条而不是拦。

### 4.3 与 `tiered_expr` 表达式里的 `hour()`：这是第二条时间轴，已经存在

`pkg/billingexpr` 提供了 `hour(tz)` / `weekday(tz)`，表达式里可以写
`hour("Asia/Shanghai") >= 22 ? ... : ...`——**按时刻变的绝对 ¥ 单价**。这恰好是
「时段价目表」的表达式写法，而且它和 Layer 4 会**叠加**（tiered 的预扣/结算同样是
`quotaBeforeGroup × GroupRatioInfo.GroupRatio`），一个模型同时配两处就是双重时间轴，
而表达式里的时间分支不出现在 `time_rule` 日志、也不进模型广场的分时表——用户看不到。

本次不合并这两套（合并等于重做表达式系统），但**必须硬互斥**（拒绝保存，不是警告）——
它们不是「两个功能」，是同一件事的两种写法，同时存在等于同一笔单乘两次时间系数。

互斥判定放在**模型级**，因为表达式是全局按模型名存的
（`billing_setting.billing_mode` / `billing_setting.billing_expr`），
按线路判解决不了「premium 走时段价、default 走表达式」这种想象出来的组合。

三道检查口径一致：**都不看当前计费模式**，只看"表达式里有没有时间函数"。

| 触发点 | 检查 | 行为 |
|---|---|---|
| 保存 `GroupTimeRatio` | `checkTimePriceVsExpr` | 命中模型的**表达式**里带时间函数 → 拒（不论模式是否为 `tiered_expr`） |
| 保存 `billing_setting.billing_expr` | `checkExprVsTimePrice` | 该模型已有时段价 → 表达式里不许出现时间函数 |
| 保存 `billing_setting.billing_mode` | `checkBillingModeVsTimePrice` | 切成 `tiered_expr` 时，若表达式带时间函数且已有时段价 → 拒 |

为什么第一条不看模式：表达式里存着 `hour()` 说明这颗雷已经埋下。它现在可能因为模式不是
`tiered_expr` 而没有生效，但切模式的那一刻就生效，而那一天不会有人回头检查"这个模型配没配
时段价"。运营要配时段价，先删掉那条旧表达式即可 —— 错误提示里就是这么写的。

代价：若现网已经同时存在「带时间函数的表达式 + 时段价」，此后保存计费模式会被拒。这种状态
本身就该清理，按提示删掉其中一处即可。后两条是补洞用的——没有它们，「先配时段价、再把模式
切成 `tiered_expr`」或「先配时段价、再给表达式加 `hour()`」都能绕过第一条。

> 2026-11-20 现网核算：`billing_setting.billing_mode` 与 `billing_setting.billing_expr`
> 都是 `{}`，**没有任何 `tiered_expr` 模型**——三道检查当前都不触发，属于为将来准备。

**检测是可行的，但要按 `|||` 切开再判，整体编译会静默漏判**（已实测）：

```
v2:tier("peak", p*5 + c*30)|||hour("Asia/Shanghai") >= 9 ? 2 : 1

UsedVars(整串)  → nil     ← 复合串编译失败（unexpected token "|"），静默返回 nil
UsedVars(part[1]) → {hour: true}   ← 切开后可检出
```

`extractUsedVars` 走的是 `ast.Find` 收集 `IdentifierNode`，函数名也会被收进
（实测 `tier` / `weekday` / `hour` 都在），所以检测函数只需按 `|||` 切分、
逐段 `UsedVars`、与白名单 `{hour, minute, weekday, month, day}` 求交——
不要用「有没有函数」判，那会把 `tier`/`max` 误判成时间函数。

未来的归宿是把时段价系数作为表达式的一个输入变量（`tf`），让一个模型只有一个时间来源；
那时这条互斥自然消解成「只有一处能写」。

### 4.4 与任务冻结：继承，无需改动，但不能挪位置

视频/图片任务结算发生在提交后几百秒。时段系数留在 `ResolveGroupRatio` 内部，
冻结值自然带上（`BillingContext.GroupRatio`、`GroupRatioInfo.TimeValue` 已冻结）。
**如果为了「只改展示」而把时段系数挪到 pricing 接口里算，冻结就会丢**——
23:59 提交、00:30 出片的任务会按结算时刻的时段计价。这是本设计里最容易做错的一步。

### 4.5 与「促销有效期」（未来项）：不同轴，可以并存

`docs/group-management-redesign.md` §10 提到的「规则生效时间窗（start/end）」是
**一次性时间区间**，属折扣轴：一条「双 11 期间 7 折」的规则，到点失效。
本设计的时段价系数是**循环时间窗**（每天/每周重复）。两者语义不同、落在不同轴，
可以同时存在，展示上也应该分开（一个是「限时优惠 7 折」，一个是「闲时价」）。
需要守住的只有一条：**折扣轴上的时间窗只允许影响折扣，不允许把时段价系数当价目基线去乘**。

### 4.6 与 `(0,1]` 校验：要放开到允许加价

放开的理由见 §2（DeepSeek 高峰 = 空闲 × 2 就是加价）。放开的代价是展示必须配套：

- `TimeRatioView.Active` 现在的判据是 `chargedValue < 1`（「此刻有优惠」）。加价档下它是假，
  而`Windows[i].Active` 为真——两个字段的语义本来就是分开的，加价不破坏它，但文案要从
  「优惠中」改成「高峰价」。
- 价格列不能无条件用「划线价 = 更高的那个」：加价档下划线价反而更低。
  处置见 §6.9。
- 建议上限 20（手误 `100` 会让整批模型在高峰白送/白收），下限保持 > 0。

### 4.7 「互斥」怎么做才对：先数清有几个时间载体

问「配了动态目录价就不能配动态折扣」之前，得先数清站内一共有几个**会让价格随时刻变**的载体。
四个候选，性质完全不同：

| 载体 | 所在轴 | 时间性质 | 现状 | 结论 |
|---|---|---|---|---|
| `GroupTimeRatio` 时段规则 | 折扣 | 循环（每天/每周） | 有 | 迁移成「时段价」（换轴，不是互斥） |
| `billingexpr` 的 `hour()` 等 | 价格 | 循环 | 有 | 与时段价**硬互斥**（§4.3） |
| 促销有效期 `start/end` | 折扣 | 区间（一次性） | 无 | **不互斥**，与时段价正交可叠加 |
| 算法式实时浮价 | 价格 | 实时 | 无 | 不做（§9.1） |

三档互斥强度，越往下越可靠：

| 强度 | 做法 | 能不能被绕过 |
|---|---|---|
| ① 校验互斥 | 配了 A 就拒绝 B | 手改 JSON、老数据、两个管理员各存各的 option key 都能绕过 |
| ② 结构互斥 | A 与 B 是同一字段的两种取值 | 绕不过，但读时必须有「谁生效」的优先级 → 又变回隐式规则 |
| ③ 语义互斥 | 另一层在类型上就没有时间字段 | 绕不过，且不需要优先级 |

**能拿 ③ 的地方一律拿 ③。** 时段价与促销有效期就是 ③：折扣轴没有时间字段，
价格轴只有一个时段系数，两者相乘是确定的。真正需要 ① 的只有时段价 × 表达式时间函数——
因为它藏在字符串里，结构上管不到。

要不要把「时段折扣（旧语义）」也做成与时段价互斥（②，读时按 `axis` 字段选路径）？
**不建议作为长期形态**：两套语义意味着解析两条路径、展示两套口径、试算器两种解释、
报表两种口径，而读时的「谁生效」就是一条隐式规则——本仓注释反复写的那句
「写错不报错、只静默算错价，是这类系统最不该出的错」说的正是这个。
如果只是为了**省掉一次性迁移**，可以让它只活在迁移窗口期：迁移前把未确认的规则标成
`axis: "discount"`，迁移工具逐条改写成 `price` 并删掉 `discount` 分支的代码。
代价说清楚：legacy 规则在迁移完成前仍然让折扣率漂移，也就是**问题只在新配置上被解决**。

### 4.8 被否掉的替代方案：用「互斥」代替「叠加」

一个很自然的想法：既然 bug 出在「时段规则 + 模型规则」同时命中，那就禁止它们同时存在。
**不行，因为它只挡住一个 bug 的一个触发口，而根因是参照对象错了。**

当前设计里的问题其实是三个，不是一个：

| # | 问题 | 互斥能否解决 |
|---|---|---|
| 1 | override 锁价被时段吃掉（2.2 → 1.05） | ✅ 能（禁止这个组合） |
| 2 | multiply 折扣被时段吃掉，且夜间值不随折扣变化 | ❌ **不能**——「常规 8 折 + 闲时再降」是核心用例，把它也互斥掉等于删功能 |
| 3 | 折扣率随时钟漂移（角标/报表） | ❌ 不能，那是展示口径 |

第 2 条的根因不是「两者都配了」，而是**时段系数的参照对象是 `Base`，不是常规价**。
同一个 `0.7`，在有 8 折的模型上意味着 5.6 折，在没有模型规则的模型上意味着 7 折——
数字的含义取决于它脚下被替换掉的那一层。改参照对象（乘在常规价上）之后，
`<1 一定更便宜、>1 一定更贵` 成为可测的不变量，第 1 条也随之消失，**不再需要互斥**。

而且互斥会制造一个新的坑：管理员以后给有时段规则的模型加 override，会收到「不允许」，
而他要的（这条贵线路夜里也便宜）是完全正当的需求。计费系统里，「拒绝回答」不如「答对」。

那当初为什么选「取代」？因为叠乘时画面上会出现两个折扣（8 折 × 7 折），要人乘。
**这个顾虑在搬到价格轴之后自动消失**：画面上变成「原价 ¥12.0 → 8 折 → ¥9.6，闲时 ¥8.4」，
只有一个折扣数字，另一个是价目。── 当初的正确直觉（别让人心算两个折扣）
和现在的叠加并不冲突，冲突的是「把时间维和折扣画在同一个轴上」。

结论：**叠加是终态，互斥退回它真正该管的范围**（§4.3 的「同一能力写两处」）。

## 5. 迁移：可以精确自动换算，override 例外

### 5.1 换算矩阵

旧终值 `= Base × tv`；新终值 `= Base × D × tf`（D = 该 (线路, 模型) 的模型乘数，无规则时 1）。
令两者相等：

| 组合 | tf 换算 | 是否自动 |
|---|---|---|
| 时段规则，无模型规则 | `tf = tv` | ✅ 值不需要动 |
| 时段 + multiply `D` | `tf = tv / D` | ✅ 精确，且与 userGroup 无关 |
| 时段 + override `V`，该线路**无身份覆盖** | `tf = tv × GroupRatio / V`（Base 恒等于 GroupRatio） | ✅ 精确，可自动 |
| 时段 + override `V`，该线路**有身份覆盖** | `tf = tv × Base / V`，Base 随 userGroup 变 | ❌ 逐用户分组不定，人工确认 |

第 2 行的「与 userGroup 无关」是关键：Base 虽被身份覆盖影响，但两边都是同一个 Base，
约掉了。例子：Base 1.5、multiply 0.8、tv 0.56 → `tf = 0.7`，
新终值 `1.5 × 0.8 × 0.7 = 0.84` = 旧终值 `1.5 × 0.56 = 0.84`。✅

override 那两行的分界很关键：**只要没人用 `GroupGroupRatio` 覆盖过这条线路，Base 就是唯一的
`GroupRatio`，override 组合也能精确保价换算**。现网如果主要靠「线路价 + 模型定价」表达价差、
身份覆盖基本不用，那么「人工确认」这一步可以退化成「选口径」而不是「逐条填数」：

| 口径 | tf | 夜间价 | 什么时候选 |
|---|---|---|---|
| **保价** | `tv × GroupRatio / V` | 与迁移前逐位相同 | 只想换语义、不想动现网价格 |
| **纠正** | 就是运营填的那个时段价（如 0.7） | `V × 0.7`，普遍高于现值 | 承认旧价位一直是错的，改回「锁价打折」 |

§4.2 的例子（1.05 vs 1.54）就是这两种口径的差。迁移工具应当**同时给出两列**，
让运营按线路一次性选口径，而不是逐模型手工算。

### 5.2 工具形态

一次性、管理员确认，不自动静默改：

1. 后端提供 `POST /api/group/time-ratio/preview-migration`：输入当前 `GroupTimeRatio` +
   当前 `GroupRatio`/`GroupModelRatio`，输出逐 `(线路, 模型模式串, 窗口)` 的
   `{old_value, old_final, new_value, new_final, auto: bool}`；
2. 前端（分组管理 → 模型价格）渲染成一张对照表，`auto=false` 的行标红要求手填；
3. 确认后走既有的 `PUT /api/option/` 写回 `GroupTimeRatio`。**不新增写接口**。

不做「双语义开关」：一个 option 字段决定语义 = 两套解析实现长期并存，
而两边一旦分叉，表现是「计价按新口径、展示按旧口径」而都不报错。迁移一次性做完更安全。

### 5.3 验收：必须逐位相等

迁移脚本的验收不是「跑通」，是**逐位相等**：

- 输入迁移前的配置，对每个 `(userGroup, 线路, 模型)` 组合，新解析的 `Final` 必须与
  迁移前 `Final` 完全一致（浮点按 1e-9）；`auto=false` 的组合除外，单列清单。
- 空 `GroupTimeRatio`：所有既有计费测试逐位不变（这是必须保住的性质，与 `GroupModelRatio`
  引入时的「P0 上线行为零变化」同源）。
- 回退验证：把 `Final = NormalRatio × tf` 改回 `Final = Base × tf`，§5.3 的用例必须见红。

### 6.1 运营的心智模型

页面顶部那条公式已经是对的（`index.jsx:368`），一个字不用改：

```
最终倍率 = 线路价（基础倍率 → 模型定价 → 时段价） × 用户档折扣
```

- **线路价**：这条线路**此刻**的价目。它随时段变，这才是「原价」。
- **用户档折扣**：合同折扣。**它不随时段变** —— 这是整套设计对客户与财务的承诺。
- **时段价填的是「相对本线路常规价的乘数」，不是绝对倍率**：填 `0.7` = 这段时间按七成收，填 `2` = 翻倍。改模型定价时时段价自动跟随，不用回头改第二遍。

一句话给运营：**「时段价」不是打折，是这条线路在那个时段标什么价；折扣永远只来自用户档。**

### 6.2 谁在哪配什么

| 配什么 | 在哪 | 影响范围 | 多久动一次 |
|---|---|---|---|
| **时段价（唯一一层）** | **设置 → 模型定价**，每个模型行上的「分时价」 | 该模型 × **全部线路（全网）** | 低 |
| 价目时段（模板） | 模型定价页「分时价」面板里维护（与分组管理共用同一份） | 全局共用，被规则引用 | 很少 |
| 常规价（线路 × 模型） | 分组管理 → 线路 → 模型定价与时段价：模式（折扣 × / 定价 =）+ 值 | 该线路该模型 | 中 |
| 用户档折扣 | 用户档 → 档位折扣 | 该档全部模型 | 低 |
| 基础倍率 | 线路 → 线路列表 | 整条线路 | 极低 |

顺序是：**上游价目变了 → 在模型定价页给模型配一次分时价 → 全网立刻生效。** 没有第二步。

**已落地（P1）**：`web/classic/src/pages/Setting/Ratio/components/TimePricePanel.jsx`
——模型定价页底部独立成卡（它写的是另一个 option key，单独保存才不会与「应用更改」互相覆盖），
内含时段模板维护、规则表（模型 / 时段 / 系数 / 折算 / 备注）、「此刻生效」提示，
以及一键「合并到全网」把按线路存的旧规则搬进 `*`。分组管理页的时段列已改为**只读展示**
（显示生效结果 + 「全网 / 线路」角标），顶部有跳转提示。
`ModelRatio` 本身（标准目录价）仍然不动 —— 分时价是乘在它上面的系数（§3.1.1）。

因为一次改动**对全网所有线路、所有用户同时生效**，面板上必须常显影响面（见 §6.0 界面稿），
这是全局层唯一比线路层更危险的地方：没有"先在一条线路上试试"的余地。

### 6.3 走查 A：跟随上游峰谷价（最常见的场景）

背景：上游公布「工作日 9:00-12:00、14:00-18:00 是高峰，其它时间半价」。

**第 0 步 先决定谁是基准** —— 这一步做错，后面每条规则都要返工

- 法则：**把常规价设成「覆盖时间最多的那一档」，只给少数时段配系数。**
- 本例：高峰只有工作日两段（共 7 小时），其余 17 小时 + 周末都算空闲 → **常规价 = 空闲价，高峰 ×2**。
- 反例：若只有「凌晨 0-6 点」特殊，则常规价 = 白天价，凌晨 ×0.6。
- 为什么：规则条数越少越不会漏；跨午夜窗口（22:00→06:00）最难核对，能避开就避开。

**第 1 步 建两个时段模板（用预设，十秒）**

- 顶部「时段模板」→ 新建：
  - `工作日高峰·上午`：时间段预设「上午工作时间 09:00-12:00」，生效日「工作日」
  - `工作日高峰·下午`：时间段预设「下午工作时间 14:00-18:00」，生效日「工作日」
- 时区默认 `Asia/Shanghai`；换成别的时区时列表会显式标出时区 —— 「09:00-12:00」不写时区，没人知道对应几点。
- 模板全局共用：改「上午高峰」的钟点，所有引用它的线路一起变（页面已有提示）。

**第 2 步 给一个模型挂时段价**

- 选线路（如 `default`）→ 规则表找到 `deepseek-chat` 行（没配过就先「添加模型」）
- 该行「常规价」：模式「折扣 ×」、值 `1`
- 「时段价」单元格点开 → 选 `工作日高峰·上午` → 值填 `2` → 行内立刻预览：

  ```
  常规 1.00x → 工作日高峰·上午 2.00x
  ```

  → 「添加」；再加 `工作日高峰·下午` ×2。
- 单元格变成两个橙色标签：`工作日高峰·上午 ×2`、`工作日高峰·下午 ×2`
- 「折算」列变成两行，这就是这个模型在两个时段各自的真实价：

  ```
  常规  1.00x
  高峰  2.00x
  ```

**第 3 步 批量（整条线路都要分时）**

- 勾选行（表头可全选）→ 批量栏「时段价」：选 `工作日高峰·上午` + 值 `2`
- 按钮文案必须带影响面：「把 12 个模型的『工作日高峰·上午』设为 常规价 ×2」
- 同一模型同一模板**已配过就改值，不追加** —— 追加会造出两条同模板规则，保存时被重叠校验拒绝，而人看不出是这次批量造成的（现有实现已这样，保留）。

**第 4 步 通配（可选，但要看清算辐射范围）**

- 加一行 `deepseek-*` + 时段价 ×2 → 该线路所有 deepseek 模型一起生效
- 通配单独一块列在精确规则**上方**，行内标「影响 7 个模型」—— 按本线路实际有渠道覆盖的模型实时算。这个数就是这次配置的爆炸半径。
- 只改一个模型就别用通配：**精确规则永远压过通配**，两者并存时通配对那个模型不生效。不写清楚这点，人会以为通配坏了。

**第 4b 步 覆盖面：模型通配 `*`**

- 模型名填 `*` → **全站所有模型**统一分时（例如"全站夜间 8 折"），一行搞定。
- 精确规则永远压过通配：某个模型要单独一套，加精确行，它整组取代 `*` 的时段表（见下）。

> ⚠️ **覆盖是「整组取代」，不是「逐窗口合并」**。`pickTimeRule` 先按具体度选出**一条**模式串的
> 窗口列表，再在那张表里挑生效档。所以给某模型配了精确行，`*` 上配的几个时段对它**全部失效**，
> 不是只替换同名时段。编辑器必须在精确行上提示「本行会整组取代 `*` 的时段价」，
> 否则运营配了「`*`: 高峰×2」再给一个模型加「深夜×0.7」，会以为它白天仍按高峰计，
> 实际它白天回到了常规价。
>
> 例外一多，`*` 的配置就被悄悄掏空了 —— 所以 `*` 只适合「全站统一，个别模型不参与」这种局面。

**第 5 步 保存与生效**

- 顶部「保存」→ 保存即对所有**新请求**生效。
- 进行中的异步任务沿用**提交时冻结**的价：23:59 提交、00:30 出片的视频不会变价。运营必须知道「改了价 ≠ 立刻所有单都变了」，否则对账时会怀疑系统。

### 6.4 走查 B：夜间短时段优惠

- 建模板 `深夜 00:00-08:00`（预设直接有）。
- 常规价不动（例如 1.20x），时段价填 `0.7` → 单元格青色标签 `深夜 ×0.7`，折算列 `深夜 0.84x`。
- 这里就是本次改动最实在的一点：**以后把模型折扣从 0.8 改成 0.75，深夜价自动变成 0.63x**，不用回来改时段价。改之前（取代语义）得手工把它从 0.56 改成 0.525，而漏改的表现只是「夜里好像贵了一点」，没人会发现。

### 6.5 三道验收关（运营自己就能验）

1. **试算器**（同页底部）：输入（用户档, 线路, 模型），把时刻拨到 `02:00` 与 `10:00` 各看一次。输出必须是两段，一眼看出哪一层随时刻变：

   ```
   价格轴  目录价 1.00 → 线路基准 1.50 → 模型定价 ×0.80 → 常规价 1.20
           → 高峰价 ×2.00 → 此刻价 2.40
   折扣轴  用户档 0.90                     （固定，与时刻无关）
   ─────────────────────────────────────
   实付    2.40 × 0.90 = 2.16
   ```

2. **模型广场**（切到该线路）：折扣角标必须**恒定**（白天夜里都是「9 折」），变的只有价格旁的标签（`高峰价` 橙 / `闲时` 青）。角标还会随时钟变 = 没改对。

3. **下一单之后看日志**：`时段价 工作日高峰·上午:×2`；`group_ratio` 是含时段价的终值，拿它乘 `model_ratio` 必须等于实扣（这条永远自洽）。

### 6.6 字段级说明与校验

| 列 | 填什么 | 允许值 / 边界 | 出错时 |
|---|---|---|---|
| 模型 | 精确名或尾部通配 `xxx-*` | `*` 只能在结尾 | 本线路无渠道覆盖 → 橙标「未匹配」，不拦保存 |
| 模式 | `折扣 ×` / `定价 =` | 两种 | `定价 =` 与基础倍率脱钩；**时段价仍乘在它上面**（锁价也能分时） |
| 值 | 折扣乘数 / 锁价倍率 | ≥ 0 | |
| 时段价 | **相对常规价的乘数** | `(0, 20]`；同模型同模板只能一条 | `<1` 青（闲时）/ `>1` 橙（高峰）；0 与负数拒绝 |
| 备注 | 为什么是这个价 | 文本 | 半年后没人记得，建议写 |

保存时会被拒的：

| 拒绝 | 文案要点 | 谁的锅 |
|---|---|---|
| 同模型两档时间重叠 | 点名线路/模型/两个模板：「必有一档永远不生效」 | 配错 |
| 引用了已删除的模板 | 「请先重建模板或改引用」 | 配错 |
| 钟点没补零（`9:00`） | 要求 `HH:MM` | 配错 |
| 该模型的分时价已写在计费表达式里 | 「`hour`/`weekday` 已在表达式里定义，不能再配时段价」（§4.3） | 重复配置 |

只警告不拦的：`定价 =` 与时段价同时存在（现在是合法且明确的组合，见 §4.2）。

### 6.8 倍率试算器（`RatioSimulator` + `POST /api/group/resolve`）

拆成两段，让「哪一层会随时间变」一眼可见：

```
价格轴   目录价 1.00 → 线路基准 1.50 → 身份覆盖 0.90 → 模型乘数 ×0.80
         → 常规价 0.72 → 闲时价 ×0.70 → 此刻价 0.504
折扣轴   用户档 1.00                        （固定，与时刻无关）
────────────────────────────────────────────
实付     0.504 × 1.00 = 0.504
```

一处必须说准的现状语义：身份折扣（`GroupGroupRatio`）是**基准覆盖**而不是乘数，
所以它落在价格轴的「基准」位置上（现有试算器也是这么摊的）。它照样是「固定的」——
只要是`(时刻 → 值)` 的常数函数，「折扣恒定」这条不变量就成立。
真正需要新加进来的只有「时段价」这一格。

接口要补 `normal_ratio`（已有 `RatioResolution.NormalRatio`，只是没下发），
否则页面上 `after_model_rule × time_value ≠ final` 又差一个说不清的系数——
那正是现在这个接口存在的理由（`controller/group_admin.go` 的注释）。

### 6.11 反例：为什么不能只改文案

「保留取代语义，只把折扣角标换个算法显示」看起来最省事，但它必然自相矛盾：

现在的实现正是为了避开这个矛盾，才把时段塞进折扣角标。
**换语义必须换算式**，展示只是让它可读。

### 8.1 滚动升级：先撤时段价，切完再按新语义配（已采纳）

现实约束：不能停服、只能滚动升级；option 每 60 秒从库里同步；新旧副本必然同时在线一段时间。
典型解法是给规则加一个「双重语义」字段（expand/contract），但那要留两套解析、两套校验、
两套测试 —— 为一个只影响 2 个模型的迁移，代价过大，**本仓没有采用**。

更简单的办法是**把迁移问题消掉**：时段规则本来就是可选配置。

```
1. 清空时段规则（rules = {}）   → 全时段按常规价 0.45，新旧码算出来完全相同
2. 滚动发版（单一语义的新代码）   → 仍是 0.45
3. 全量新码后重新配置           → 直接填 1.1111，本来就是新语义，不需要兼容
```

**为什么成立**：没有命中时段时，新旧两条公式退化成同一个数 ——
旧码 Base × 模型折扣、新码 常规价，都是 1.0 × 0.45 = 0.45。
所以「删规则」在任何时刻执行都不会错价，滚动窗口里新老副本混跑也不会错价。

**代价**：第 1 步到第 3 步之间，工作时段价格是 0.45 而不是 0.5 —— 少收 10%。
方向对客户有利（不会多收、无退款风险），且只影响 default 线路的 2 个模型。
想连这 10% 都避免，就把第 1 步放在工作日 18:00 之后或周末 —— 那时规则本就不命中。

**回滚**同理：先清空规则回到 0.45，再回退镜像。

**前提（写下来免得以后踩）**：这套办法依赖「时段规则不覆盖全天」。若某天配了全天生效的
时段价，第 1、2 步之间就会真实变价，那时必须回到「双语义字段」或停机切换。

落地 SQL（Step 1：清空规则但保留 windows 模板，第 3 步要复用）：

```sql
UPDATE options SET "value" = jsonb_set("value"::jsonb, '{rules}', '{}'::jsonb)::text WHERE "key" = 'GroupTimeRatio';
```

Step 3 重新配置 —— **首选走 UI**（设置 → 模型定价 → 分时价 → 添加时段价），
因为写库会绕过保存校验，形状错了不会报错、只会静默不生效。

确实要走 SQL 时，**注意 `rules` 下面还有一层作用域键**：时段价挂在保留键 `"*"`（全网）下，
写成 `{"模型": [...]}` 会让 `GroupTimeRatio` 反序列化失败，各副本加载失败后一直停在
Step 1 留下的 `rules = {}`，而计费照旧按常规价跑 —— 全程没有任何报错。

```sql
UPDATE options SET "value" = jsonb_set("value"::jsonb, '{rules}',
  '{"*": {"deepseek-v4-1-flash":[{"window":"window_1","value":1.1111},{"window":"window_2","value":1.1111}],
          "deepseek-v4-1-flash-1017":[{"window":"window_1","value":1.1111},{"window":"window_2","value":1.1111}]}}'::jsonb)::text
WHERE "key" = 'GroupTimeRatio';

-- 落库后必须确认形状：结果里应当能看到 "*" 这一层
SELECT jsonb_pretty("value"::jsonb -> 'rules') FROM options WHERE "key" = 'GroupTimeRatio';
```

## 9. 不做 / 已知限制

1. **不做算法式动态目录价**（按负载/时段自动浮价）。预扣、结算、对账、对外报价都要求价格
   在请求时刻可确定、可复述；只有「公布式分时价目」是安全的。
2. **不动 `ModelRatio` 的数据结构**。它是全局 `map[string]float64`，被约 20 个文件读
   （套餐折算、积分价、成本比、视频矩阵锚点、单位迁移……），改成带时段的对象会让
   「目录价」这个数在所有那些地方都变成「此刻的目录价」，blast radius 远大于收益。
   本设计让时段价系数按 `模型` 索引、乘在 `ModelRatio` 之上，作用域收在 `ResolveGroupRatio` 内部。
3. **只做 classic + mobile 两个主题**（仓库里没有 web/default，`AGENTS.md`/`CLAUDE.md` 里那句已过期），两端口径必须一致。
4. **不做双语义开关**（§5.2）。
5. **跨时段边界的页面驻留**：模型广场开着不动跨过边界仍显示旧价，下单按新价扣。
   这是既有已知限制，本次不解决。
6. 顺带发现（不属于本次范围）：`docs/group-concepts.md` 被 `types/price_data.go`、
   `controller/pricing.go`、`service/log_info_generate.go`、`model/user_cache.go` 等近十处
   引用为「解析链权威说明」，但文件不存在——这些引用目前是死链。

## 10. 现网快照（2026-11-20）

生产库 options 导出后本地跑 `scripts/time_price_migration_report.py` 的结论。规模很小，
结论是：**现状结果与运营意图一致**，但它靠的是一个很脆的巧合。

**面**：6 条线路（`default / dev / oversea / ovaijisuan / vip001 / shenhe`，**基准全部为 1**）、
`UserGroupModelRatio` 空、`GroupGroupRatio` 空、无停用线路。
时段规则只有 **1 条线路（default）**、**3 个模型 × 2 个窗口 = 6 条**，**没有 override**，全是 multiply 0.45。

运营意图（2026-11-20 确认）：**工作时段算力紧缺 → 贵一点（5 折）；平时算力空闲 → 便宜一点（4.5 折）**。

| 模型 | 模型定价 | 时段值（工作时间） | 实际（工作时段） | 实际（其余时段） |
|---|---|---|---|---|
| deepseek-v4-1-flash | ×0.45 | 0.5 | 0.5 | 0.45 |
| deepseek-v4-1-flash-1017 | ×0.45 | 0.5 | 0.5 | 0.45 |
| deepseek-v4-flash-vision | ×0.45 | 0.5 | 0.5 | 0.45 |

### 10.1 结果是对的，但它是「取代」凑出来的

`Base(1) × 0.5 = 0.5` 恰好等于运营想要的紧缺价——可运营配的 `0.45` 在命中时段时是**被整条丢掉**的，
并没有参与计算。也就是说：这两档价（0.45 / 0.5）之间**没有配置上的关系**，只有数值上的巧合。

后果就是维护陷阱：把模型定价从 `0.45` 改成 `0.40`，工作时段**仍然是 0.5**，
两档差距从 +11% 悄悄变成 +25%，而页面上看不出任何异常。这正是本次要改的那件事。

### 10.2 迁移口径：保价，系数 1.1111（并要求允许 >1）

叠加之后正确的写法是「常规价 = 空闲价 0.45，紧缺时段 × 0.5/0.45」：

| 口径 | 时段系数 | 工作时段 | 其余时段 | 评价 |
|---|---|---|---|---|
| **保价**（推荐） | **1.1111** | 0.5 | 0.45 | 价格完全不变，且从此跟随模型定价 |
| 纠正 | 0.5 | 0.225 | 0.45 | ❌ 变成 4.5 折再打 5 折，运营意图不是这个 |
| 删规则 | — | 0.45 | 0.45 | ❌ 丢掉了紧缺加价 |

结论：**§4.6「要不要允许系数 > 1」不是理论问题，现网第一个迁移就需要 1.1111。**
不允许加价，这个需求根本表达不出来。建议上限 20，`>1` 在管理端显示成「比常规贵 11%」而不是「×1.11」。

### 10.3 摊平到全局层：已确认可行

时段规则目前只挂在 `default`，而 `abilities` 显示这 4 条线路卖的是**同一批算力**：

```
default / dev / ovaijisuan / vip001  →  channel_id 1  "gpustack-default"  priority 100
模型：deepseek-v4-1-flash、deepseek-v4-1-flash-1017
```

同一张卡、同一个模型、同样的紧缺时段——**价格却只有 default 一条线路随供需变动**，这本身就是
定价不一致。所以摊平不仅可行，而且顺手修正了它：

| 线路 | 今天（工作时段 / 其余） | 摊平后 | 说明 |
|---|---|---|---|
| `default` | 0.5 / 0.45 | 0.5 / 0.45 | 不变 |
| `ovaijisuan` | 0 / 0 | 0 / 0 | 内部免费，乘任何系数仍是 0 |
| `vip001` | 1.0 / 1.0 | **1.111** / 1.0 | 工作时段 +11%（此前没跟上供需价） |
| `dev` | 1.0 / 1.0 | **1.111** / 1.0 | 同上 |

**这两条 +11% 需要业务点头**（尤其 `vip001` 若涉及合同固定价）：它逻辑上正确，
但确实是对两条线路的提价。

顺带两条清理项：

- **`deepseek-v4-flash-vision` 没有任何 abilities（含 disabled）** → 既没有渠道可服务，却配了
  模型定价 `0.45` 和两条时段规则。**2026-11-20 已处理**：时段规则已从 `default` 删掉；
  模型定价与 `ModelRatio` 残留按运营判断保留（无渠道即不可计费，属于惰性配置，只会让健康面板
  显示「未匹配」）。
- 因此迁移面从 3 个模型缩到 **2 个模型 × 2 个窗口 = 4 条规则**，值 `0.5 → 1.1111`。
- `vip001` 上那两个全价模型（1.0）在一条 VIP 专用线路上相当可疑，建议顺带核对是不是配漏了。


### 10.4 踩坑记录：删行把时段规则变成「看不见的孤儿」

2026-11-20 现网操作：在「模型定价与时段价」里删掉了 `deepseek-v4-flash-vision` 那一行，
UI 上时段 tag 随之消失，但库里 `GroupTimeRatio.rules.default` 仍然留着它的两档规则，
而**页面上再也没有入口去删它们**。

根因是两处实现的分工：`removeRow` 只改 `GroupModelRatio`（行），时段价存在**另一个**
option key（`GroupTimeRatio`）里，而 tag 只渲染在行上。行一没，人就再也够不着它。

处置：① P1 必须让删行顺带删时段价，或至少拦截并提示；② 存量孤儿用 SQL 清理
（`jsonb_set` 去掉 rules.default 下的那个 key）；③ 这类「跨 option key 的从属关系」
在本仓已有先例（§3.2 的模板引用、线路引用），处理原则一致：**要么同 key 硬校验，要么体检可见**。
